# Фаза 2 — Автоматизация. Движок правил

Техническое задание и договорённости по реализации. Читать вместе с `docs/ROADMAP.md`
(что и зачем) и `docs/OPERATIONS.md` (как это эксплуатировать).

**Тезис фазы:** конструктор важнее набора готовых сценариев. Готовые сценарии закрывают
десять случаев из ста, конструктор — восемьдесят. Оставшиеся двадцать закрывает вебхук.

**Главное требование:** автоматизация не должна быть чёрным ящиком. Журнал срабатываний
и тестовый прогон — не «приятное дополнение», а обязательная часть поставки: именно
непрозрачность роботов Битрикс24 — самая частая претензия к ним. Правило, про которое
нельзя ответить «почему оно сработало и что именно сделало», считается несделанным.

---

## 1. Границы фазы

Входит:

| Блок | Суть |
|---|---|
| Движок правил | событие → условия → действия, единый для всех сущностей |
| Журнал срабатываний | каждый запуск с входом, решением по условиям и результатом каждого действия |
| Тестовый прогон | «что было бы» на реальной записи, без единой записи в базу |
| Визуальный редактор | канва: событие, ветки условий, действия; без кода |
| Распределение обращений | по очереди, по загрузке, по каналу, по ответственному за клиента |
| SLA | время первого ответа и решения, счётчик в инбоксе, эскалация руководителю |
| Расписание и часовые пояса | автоответ вне рабочих часов, запрет ночных звонков клиенту |
| Сценарный бот квалификации | собирает бюджет, сроки, задачу; отдаёт диалог человеку |

Не входит (следующие фазы): готовые «маркетплейсы сценариев», A/B-ветвление рассылок,
ML-скоринг, редактор писем с версткой. Действие «отправить письмо» использует шаблоны
быстрых ответов и печатные формы из фазы 1.

## 2. Модель: событие — условие — действие

Одна сущность `automations` описывает правило целиком. Ветвление хранится деревом узлов,
а не таблицей «условие → действие»: это позволяет редактору рисовать канву, а движку —
обходить дерево, не собирая его из плоских строк.

```jsonc
{
  "trigger": { "type": "stage_changed", "pipeline_id": 1, "to": "proposal" },
  "conditions": {                       // корневой узел: И / ИЛИ / НЕ
    "op": "and",
    "items": [
      { "field": "deal.amount", "cmp": "gte", "value": 100000 },
      { "field": "contact.tags", "cmp": "contains", "value": "vip" }
    ]
  },
  "actions": [
    { "type": "create_task", "params": { "kind": "call", "title": "Позвонить по КП", "due_in_hours": 4 } },
    { "type": "send_message", "params": { "quick_reply_id": 2 } },
    { "type": "webhook", "params": { "url": "https://...", "secret_ref": "WEBHOOK_SECRET_1" } }
  ],
  "else_actions": [],                   // ветка «условия не выполнились», необязательна
  "limits": { "once_per_entity": true, "cooldown_minutes": 60, "max_per_hour": 100 }
}
```

### 2.1 События

| Код | Когда | Контекст |
|---|---|---|
| `conversation_created` | новое обращение в инбоксе | conversation, contact, channel |
| `message_received` | входящее сообщение | conversation, message, contact |
| `stage_changed` | смена стадии сделки | deal, from, to, pipeline, contact |
| `deal_created` | создана сделка | deal, contact |
| `no_reply` | нет ответа сотрудника N часов | conversation, last_message |
| `task_overdue` | задача просрочена | task, assignee, deal |
| `field_date` | наступила дата в поле (`deal.close_date`, `contact.birthday`) | сущность |
| `payment_received` | заказ перешёл в оплаченный | order, deal, contact |
| `sla_breached` | нарушен срок первого ответа или решения | conversation, sla |

Первые пять — синхронные: их порождают уже существующие точки кода (`inbox.ingest`,
`routes/crm.js` при смене стадии). Остальные — отложенные: их находит планировщик,
опрашивая базу раз в минуту. Разделение принципиально: синхронные события не должны
задерживать ответ пользователю, поэтому исполнение всегда уходит в очередь.

### 2.2 Условия

Плоский предикат `{ field, cmp, value }` внутри узлов `and` / `or` / `not`.
Поле адресуется путём: `deal.amount`, `contact.tags`, `conversation.channel_type`,
`task.kind`, `order.total`, `user.role`, `now.weekday`, `now.hour`.

Операторы: `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `contains`, `not_contains`,
`empty`, `not_empty`, `in`, `changed_to`, `older_than_hours`.

Значения приводятся к типу поля перед сравнением: строка `"100000"` из редактора
и число `100000` из базы должны сравниваться одинаково.

### 2.3 Действия

| Код | Параметры | Заметки |
|---|---|---|
| `create_task` | kind, title, description, due_in_hours, assignee (`owner`/`round_robin`/id) | использует `server/tasks.js` |
| `send_message` | quick_reply_id или text, channel | уходит в канал диалога через `server/inbox.js` |
| `send_email` | to (`contact`/адрес), subject, body, attach (`invoice`/`quote`) | вложение рендерит `server/documents.js` |
| `change_stage` | stage_code | обязательные поля стадии проверяются, как и для человека |
| `assign` | strategy или user_id | общий код с распределением обращений |
| `add_tag` / `remove_tag` | tag | контакт или сделка |
| `set_field` | field, value | только белый список полей |
| `webhook` | url, method, headers_ref, payload_template | тайм-аут 10 с, три попытки с ростом паузы |
| `notify_manager` | text | письмо руководителю, используется эскалацией SLA |
| `wait` | hours | продолжение сценария откладывается, состояние в `automation_waits` |

Ключевое ограничение: **действие `change_stage` не обходит проверки фазы 1.** Если стадия
требует суммы или причины отказа, автоматизация получит ту же ошибку, что и менеджер,
и запишет её в журнал. Автоматизация, умеющая портить данные тише человека, хуже её отсутствия.

## 4. Исполнение

```
событие  →  server/automation/bus.js      emit(type, context)
         →  подбор активных правил по trigger_type (кэш в памяти, сброс при правке)
         →  очередь в памяти с ограничением параллелизма
         →  для каждого правила: evaluate(conditions) → run(actions)
         →  запись automation_runs
```

Правила поведения, которые нельзя нарушать:

1. **Событие не блокирует пользователя.** `emit` кладёт задачу в очередь и возвращает
   управление. Ответ HTTP не ждёт ни вебхука, ни письма.
2. **Отказ автоматизации не отменяет действие человека.** Смена стадии сохранена, даже
   если правило упало. Ошибка живёт в журнале, а не в отклике API.
3. **Защита от петли.** Действие правила порождает событие; глубина цепочки ограничена
   (`AUTOMATION_MAX_DEPTH`, по умолчанию 3), контекст несёт `origin_run_id`. Правило
   не запускается повторно от собственного действия.
4. **Идемпотентность.** `once_per_entity` и `cooldown_minutes` проверяются по
   `automation_runs` — перезапуск процесса не приводит к повторной отправке.
5. **Порядок.** Правила одного события выполняются по `priority`, затем по `id`.
   Действия внутри правила — строго последовательно; упавшее действие не отменяет
   предыдущие, но останавливает следующие и помечает запуск `failed`.

Отложенные события и `wait` обслуживает существующий `server/scheduler.js`:
одна задача `automation-tick` раз в минуту. Как и напоминания фазы 1, она не запускается
повторно поверх незавершённой и выключается нулём в переменной окружения на лишних узлах.

## 5. Прозрачность: журнал и тестовый прогон

**Журнал** пишется на каждый запуск, включая несработавший. В карточке запуска видно:

- что произошло (событие, сущность, время, инициатор);
- какие условия проверялись и **чем каждое закончилось** — не «не подошло», а
  «`deal.amount` = 40 000 < 100 000»;
- какие действия выполнены, с результатом каждого: идентификатор созданной задачи,
  код ответа вебхука, текст ошибки почтового провайдера;
- сколько заняло исполнение.

Хранение — 90 дней (`AUTOMATION_LOG_KEEP_DAYS`), чистка тем же планировщиком.

**Тестовый прогон** — `POST /api/automations/:id/dry-run` с идентификатором реальной
записи. Движок исполняет правило с подменённым исполнителем действий: ничего не пишется,
ничего не отправляется, возвращается тот же отчёт, что попал бы в журнал, с пометкой
`dry_run`. Требование к реализации: подменяется **только** слой действий, ветвление
и приведение типов идут по тому же коду — иначе тест проверяет не то, что работает в бою.

В редакторе тестовый прогон обязателен перед включением нового правила: кнопка
«Включить» активируется после успешного прогона. Это дешёвая привычка, экономящая
разосланные не тем клиентам сообщения.

## 6. Визуальный редактор

Канва на нативном SVG, без библиотек — ограничение «ноль зависимостей» остаётся в силе.

- Узлы трёх типов: событие (один, входной), условие (ветвление да/нет), действие.
- Перетаскивание мышью, привязка к сетке, связи — кривые Безье.
- Инспектор справа: параметры выделенного узла; поля подставляются из справочника
  доступных путей, а не вводятся руками.
- Схема сохраняется как JSON `definition`; координаты узлов лежат рядом с логикой
  и на исполнение не влияют.
- Панель снизу: последние двадцать срабатываний этого правила и кнопка тестового прогона.

Резервный путь: тот же сценарий редактируется списком «если — то» без канвы.
Список остаётся доступным всегда — на узком экране канва бесполезна.

## 7. Распределение входящих обращений

Очередь (`assignment_queues`) выбирает исполнителя по одной из стратегий:

| Стратегия | Правило |
|---|---|
| `owner` | ответственный за клиента, если он есть и в строю — приоритетнее прочих |
| `round_robin` | по кругу, курсор хранится в очереди |
| `load` | наименьшее число открытых диалогов и задач на сегодня |
| `channel` | закреплённые за каналом сотрудники |

Порядок: сначала `owner`, затем выбранная стратегия. Кандидаты фильтруются по
рабочему расписанию: назначать диалог тому, кто вне смены, бессмысленно. Если подходящих
нет — диалог остаётся неназначенным и попадает в очередь эскалации, а не «назначается хоть кому».

Назначение вызывается автоматически на `conversation_created` и доступно действием
`assign` в любом правиле.

## 8. SLA

Политика задаёт два срока: **первый ответ** и **решение**. Оба считаются в рабочих
минутах по расписанию: обращение в 23:50 в пятницу не съедает выходные.

- При создании диалога заводится `sla_states` с расчётными дедлайнами.
- Первый исходящий ответ проставляет `first_response_at`; закрытие диалога — `resolved_at`.
- Счётчик в инбоксе показывает остаток: зелёный при запасе больше половины, обычный
  при остатке, подчёркнутый при просрочке. Цвета нет — монохромная тема сохраняется,
  срочность передаётся плотностью и подчёркиванием.
- Просрочка порождает событие `sla_breached`: правило по умолчанию ставит задачу
  ответственному и уведомляет руководителя из `escalate_to`.

Отчёт по SLA (доля ответов в 15 минут — метрика успеха из плана) собирается в фазе 5,
но данные для него копятся с первого дня фазы 2.

## 9. Рабочее расписание и часовые пояса

`work_schedules` хранит рабочие интервалы по дням недели, праздники и часовой пояс.
Пояс клиента — в `contacts.timezone`, определяется по коду города телефона или
проставляется вручную.

Два обязательных эффекта:

1. **Автоответ вне рабочих часов.** Входящее сообщение вне смены получает ответ
   «мы работаем с 9 до 18, ответим утром» — один раз за нерабочий период, не на каждое
   сообщение. Текст берётся из шаблонов быстрых ответов, поэтому правится без разработчика.
2. **Запрет ночных звонков.** Задача с типом «звонок» не ставится на время, когда
   у клиента ночь: срок переносится на ближайшее рабочее утро **его** часового пояса.
   Приём, на котором построена EnvyCRM: менеджер не должен считать разницу с Владивостоком
   в уме — систему для того и покупают.

Расчёт живёт в одном модуле `server/schedule.js`: и SLA, и задачи, и автоответы должны
одинаково понимать, что такое «рабочее время», иначе разъедутся.

## 10. Сценарный бот квалификации

Линейный сценарий с ветвлением: вопрос → сохранение ответа в поле → следующий шаг.
Собирает бюджет, сроки и задачу до передачи менеджеру.

- Ответы складываются в `bot_sessions.answers` и по завершении переносятся в поля сделки
  (`amount`, `next_step`) и в ленту активности — менеджер видит контекст, а не «привет».
- Передача человеку: по кнопке, по ключевому слову («оператор», «менеджер», «человек»),
  по числу непонятых ответов подряд и по истечении таймаута. Любой из путей ставит
  `status = handed_over`, снимает бота с диалога и назначает исполнителя через очередь.
- Бот не работает молча: каждый шаг пишется в ленту, диалог с ботом читается так же,
  как переписка с человеком.

Ограничение честное: это сценарный бот, не языковая модель. Свободный текст он не понимает
и не притворяется, что понимает, — на непонятое отвечает передачей менеджеру. Умный
ассистент — фаза 7.

## 11. API

```
GET    /api/automations                     список с последним срабатыванием
POST   /api/automations                     создать (по умолчанию выключено)
GET    /api/automations/:id                 правило целиком
PUT    /api/automations/:id                 сохранить схему
PATCH  /api/automations/:id                 включить/выключить, приоритет
DELETE /api/automations/:id                 удалить
POST   /api/automations/:id/dry-run         тестовый прогон на реальной записи
GET    /api/automations/:id/runs            журнал срабатываний правила
GET    /api/automation-runs                 общий журнал с фильтрами
GET    /api/automations/meta                справочник событий, полей, операторов, действий

GET    /api/queues        POST /api/queues        PATCH /api/queues/:id
GET    /api/sla-policies  POST /api/sla-policies  PATCH /api/sla-policies/:id
GET    /api/schedules     POST /api/schedules     PATCH /api/schedules/:id
GET    /api/bot-scripts   POST /api/bot-scripts   PATCH /api/bot-scripts/:id
```

`meta` — не украшение: редактор строит выпадающие списки полей и операторов из неё,
поэтому новое поле или действие появляется в интерфейсе без правки фронтенда.

## 12. Структура кода

```
migrations/004_automation.sql
server/
  automation/
    bus.js         emit, очередь, ограничение параллелизма и глубины
    engine.js      исполнение правила: условия, действия, запись журнала
    conditions.js  разбор дерева условий, приведение типов, объяснение решения
    actions.js     реестр действий; действия регистрируются, а не вшиваются в switch
    triggers.js    подписка на синхронные события, поиск отложенных
  schedule.js      рабочее время, часовые пояса, перенос на ближайшее рабочее окно
  assignment.js    выбор исполнителя: owner, очередь, загрузка, канал
  sla.js           расчёт дедлайнов, фиксация ответа, эскалация
  bot.js           сценарный бот: шаги, ответы, передача человеку
  routes/automations.js, routes/queues.js, routes/sla.js, routes/bot.js
public/js/views/
  automations.js   список правил, журнал, тестовый прогон
  canvas.js        редактор на SVG
test/
  automation.test.js   события, условия, действия, петли, идемпотентность
  conditions.test.js   приведение типов и объяснения — без базы
  schedule.test.js     рабочее время, переносы, часовые пояса, праздники
  sla.test.js          дедлайны в рабочих минутах, эскалация
  bot.test.js          прохождение сценария и передача человеку
```

Действия — реестр, а не `switch`: добавление действия должно быть одним файлом
и одной строкой регистрации, иначе через полгода `engine.js` превратится в свалку.

## 13. Что проверяем тестами

Обязательный минимум, без которого фаза не считается сданной:

1. Событие смены стадии запускает правило и создаёт задачу с верным сроком.
2. Не выполнившееся условие пишет в журнал **почему** — с фактическим значением поля.
3. Тестовый прогон не создаёт ни одной записи и возвращает тот же отчёт.
4. `once_per_entity` и `cooldown_minutes` не дают сработать дважды, в том числе
   после перезапуска процесса.
5. Правило, чьё действие порождает то же событие, останавливается на предельной глубине.
6. Действие `change_stage` спотыкается об обязательные поля стадии и пишет ошибку в журнал,
   а не портит данные.
7. Упавший вебхук не отменяет уже созданную задачу и не роняет исполнение остальных правил.
8. Ошибка автоматизации не меняет код ответа исходного HTTP-запроса пользователя.
9. Распределение по кругу обходит всех, пропускает нерабочих и не назначает уволенных.
10. SLA считается в рабочих минутах: обращение вечером пятницы не просрочивается за выходные.
11. Задача на звонок клиенту во Владивостоке переносится на его рабочее утро.
12. Автоответ вне рабочих часов уходит один раз, а не на каждое сообщение.
13. Бот собирает ответы, переносит их в сделку и отдаёт диалог человеку по ключевому слову.
14. Новые таблицы попадают в резервную копию.

## 14. Наблюдаемость и эксплуатация

Метрики Prometheus рядом с существующими:

```
automation_runs_total{automation, status}
automation_duration_seconds{automation}
automation_queue_depth
automation_action_failures_total{action}
sla_breaches_total{policy, kind}
```

Переменные окружения:

```
AUTOMATION_ENABLED=true            выключатель на весь движок
AUTOMATION_TICK_SECONDS=60         период отложенных событий, 0 — выключить на узле
AUTOMATION_MAX_DEPTH=3             защита от цепной реакции
AUTOMATION_CONCURRENCY=4           параллельных исполнений
AUTOMATION_LOG_KEEP_DAYS=90        хранение журнала
WEBHOOK_TIMEOUT_MS=10000           тайм-аут исходящего вебхука
```

Аварийный выключатель обязателен: при разошедшемся правиле администратор должен уметь
погасить весь движок одной переменной и перезапуском, не разбираясь ночью в схеме.
Отдельно — выключение конкретного правила через `PATCH`, без деплоя.

## 15. Порядок работ

| Неделя | Что делаем | Почему в этом порядке |
|---|---|---|
| 1 | Миграция, шина событий, движок, журнал, тестовый прогон, API, список правил в интерфейсе | Прозрачность закладывается первой, а не прикручивается потом |
| 2 | Реестр действий целиком, отложенные события, `wait`, защита от петель | Без действий движок бесполезен, без защиты — опасен |
| 3 | Расписание и часовые пояса, распределение обращений | На них опираются SLA и автоответы |
| 4 | SLA, счётчик в инбоксе, эскалация | Требует расписания из недели 3 |
| 5 | Визуальный редактор на канве | Осмысленно рисовать то, что уже работает списком |
| 6 | Сценарный бот, шлифовка, документация, нагрузочная проверка | Бот — надстройка над готовым движком |

Готовность фазы определяется не числом закрытых задач, а тем, что владелец отдела продаж
может сам, без разработчика: собрать правило, прогнать его вхолостую, включить,
через день открыть журнал и объяснить каждое срабатывание.
