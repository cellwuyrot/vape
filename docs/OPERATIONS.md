# Эксплуатация RuCRM

Документ для того, кто держит систему в бою: как обновлять схему, переезжать на
PostgreSQL, хранить вложения, снимать и проверять резервные копии, читать логи и метрики.

---

## 1. Миграции схемы

Схема больше не создаётся при старте одним `CREATE TABLE IF NOT EXISTS`. Каталог
`migrations/` содержит нумерованные файлы, применённые версии лежат в таблице
`schema_migrations`, недостающие накатываются при запуске приложения.

```bash
npm run migrate      # накатить отдельно, до старта приложения
```

**Как добавить миграцию.** Создайте `migrations/003_короткое_имя.sql`. Внутри пишите
обычный SQL с тремя подстановками, которые раскрываются под каждую СУБД:

| Подстановка | SQLite | PostgreSQL |
|---|---|---|
| `{{PK}}` | `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGSERIAL PRIMARY KEY` |
| `{{NOW}}` | `(datetime('now'))` | ISO-строка через `to_char(now() …)` |
| `{{REAL}}` | `REAL` | `DOUBLE PRECISION` |

Правила, которые экономят нервы:

* **Применённую миграцию не правят.** Раннер хранит контрольную сумму файла и
  отказывается стартовать, если содержимое изменилось. Нужна поправка — новая миграция.
* **Каждая миграция в транзакции.** Упала на третьей инструкции — откатились все три,
  версия не записалась.
* **Пишите обратимо по данным.** Удаление колонки — отдельная миграция, выпущенная
  после того, как код перестал её читать; иначе откат релиза уронит сервис.

Старая база версии 2.0.0 обновляется без потерь: миграция 001 идемпотентна, существующие
таблицы не пересоздаются, данные остаются на месте.

## 2. Переезд на PostgreSQL

SQLite остаётся умолчанием для демо и небольших команд. PostgreSQL включается одной
переменной — прикладной код не меняется:

```bash
DATABASE_URL=postgres://rucrm:пароль@db.example.ru:5432/rucrm?sslmode=require
```

Драйвер написан на чистом Node (`server/drivers/pg-protocol.js`) — обещание «ставится
без доступа к npm-реестру» сохранено. Поддержаны: TLS, аутентификация MD5 и
SCRAM-SHA-256, пул соединений, расширенный протокол с параметрами.

| Параметр строки подключения | Зачем |
|---|---|
| `sslmode=disable\|prefer\|require\|verify-full` | `prefer` по умолчанию; для управляемых баз ставьте `require` |
| `sslrootcert=/путь/root.crt` | корневой сертификат Яндекса или VK для `verify-full` |
| `search_path=схема` | своя схема в общей базе |
| `application_name=rucrm` | различать соединения в `pg_stat_activity` |

**Порядок переезда.**

1. Поднимите базу, создайте пользователя и БД.
2. `DATABASE_URL=… npm run migrate` — схема создастся с нуля.
3. Перенесите данные. Для небольшой базы достаточно выгрузки из копии:
   `npm run backup` на SQLite даёт архив с `database.sqlite`.
4. Запустите приложение с `DATABASE_URL` и проверьте `/api/ready`.
5. Первую неделю держите SQLite-файл — откат сводится к снятию переменной.

**Что проверить на своём стенде.** В песочнице разработки живой базы нет, поэтому
интеграционный тест включается только при заданном `DATABASE_URL`:

```bash
docker compose --profile postgres up -d postgres
DATABASE_URL=postgres://rucrm:rucrm@localhost:5432/rucrm?sslmode=disable npm test
```

Без переменной этот файл пропускается, а протокол всё равно проверяется:
`test/pg-handshake.test.js` поднимает мок-сервер, говорящий на настоящем протоколе 3.0,
и прогоняет через него боевой драйвер, включая проверку доказательства SCRAM.

## 3. Вложения и файловое хранилище

Два бэкенда за одним интерфейсом (`server/storage.js`):

* `local` — каталог `DATA_DIR/files`. Годится, пока сервер один.
* `s3` — S3-совместимое хранилище в РФ. Обязательно, как только серверов больше одного.

```bash
STORAGE_BACKEND=s3
S3_ENDPOINT=https://storage.yandexcloud.net   # VK: https://hb.ru-msk.vkcloud-storage.ru
S3_REGION=ru-central1
S3_BUCKET=rucrm-files
S3_ACCESS_KEY_ID=…
S3_SECRET_ACCESS_KEY=…
```

Подпись SigV4 реализована на `node:crypto` и сверена с эталонным вектором AWS.

Особенности, о которых стоит знать:

* **Локальный каталог — запасной путь.** Если S3 недоступен в момент записи, файл
  сохраняется на диск и помечается бэкендом `local`. Обращение клиента не теряется
  из-за чужой аварии; в логе появится `storage.fallback`.
* **Файлы отдаются через приложение**, а не прямой ссылкой в бакет: иначе персональные
  данные утекают по ссылке в обход прав доступа. Каждое скачивание пишется в журнал 152-ФЗ.
* **Исполняемые расширения не принимаются** (`.exe`, `.js`, `.sh` и подобные),
  ответ всегда `Content-Disposition: attachment`.

## 4. Резервное копирование

Копия — один файл `rucrm-<метка>.tar.gz` рядом с `.sha256`. Внутри: `manifest.json`
(версия схемы, СУБД, счётчики строк), снимок базы и вложения. Список таблиц задан
константой `DATA_TABLES` в `server/migrate.js`: добавляя таблицу новой миграцией,
допишите её туда же, иначе данные не попадут в копию. В фазе 1 к списку добавились
`pipelines`, `pipeline_stages`, `lost_reasons`, `tasks`, `quick_replies`, `activities`,
`import_runs` и `doc_templates`.

```bash
npm run backup          # снять копию, проверить, ротировать, выгрузить в S3
npm run restore-check   # проверить последнюю копию, ничего не меняя
npm run restore-check /path/rucrm-2026-08-04T03-30-00.tar.gz
```

**Проверка восстановления обязательна и включена по умолчанию.** Сразу после снятия
архив разворачивается во временный каталог, база поднимается заново, счётчики строк
сверяются с манифестом. Копия, которую ни разу не разворачивали, копией не считается.

Расписание — на выбор:

* **Внутри процесса** (`BACKUP_ENABLED=true`): работает там, где внешнего cron нет —
  Render, Timeweb Cloud Apps, Yandex Serverless Containers.
* **systemd-таймер** (`deploy/rucrm-backup.timer`): классический сервер. В этом случае
  выключите `BACKUP_ENABLED`, иначе копии будут сниматься дважды.

Ненулевой код возврата `npm run backup` означает, что копия не снята или не прошла
проверку. Повесьте на это оповещение — молчаливо сломанный бэкап хуже отсутствующего.

**Восстановление вручную:**

```bash
tar xzf rucrm-2026-08-04T03-30-00.tar.gz -C /tmp/restore
systemctl stop rucrm
cp /tmp/restore/database.sqlite /var/lib/rucrm/rucrm.db
cp -r /tmp/restore/files/. /var/lib/rucrm/files/
systemctl start rucrm
```

Для PostgreSQL внутри архива лежит `database.jsonl` — построчная выгрузка вида
`{"table":"contacts","row":{…}}`, читаемая любым скриптом.

## 5. Фоновые задачи и напоминания

Внутри процесса работает планировщик (`server/scheduler.js`). В фазе 1 к резервному
копированию добавилась рассылка напоминаний о задачах:

| Задача | Интервал | Переменная |
|---|---|---|
| `task-reminders` | каждые 5 минут | `TASK_REMINDER_INTERVAL_MINUTES` |
| `backup` | раз в сутки | `BACKUP_INTERVAL_HOURS`, включается `BACKUP_ENABLED` |

Напоминание уходит на почту исполнителя, когда наступает `remind_at`. Повтор исключён
флагом `tasks.reminded` в базе, поэтому перезапуск сервиса не приводит ко второму письму.
Без настроенного `SMTP_URL` текст напоминания печатается в лог — это режим разработки,
в бою почтовый провайдер обязателен, иначе задачи молча останутся без напоминаний.

Задача не запускается повторно, пока не завершилась предыдущая: на большой базе рассылка
может идти дольше интервала. Пропуск фиксируется записью `scheduler.overlap` в логе.

При нескольких экземплярах приложения планировщик работает в каждом — напоминания
разошлются по числу экземпляров. Пока это не решено выбором лидера, оставляйте фоновые
задачи включёнными ровно на одном узле (`BACKUP_ENABLED=false` и
`TASK_REMINDER_INTERVAL_MINUTES=0` на остальных).

## 6. Логи

Формат — по строке JSON на событие (`LOG_FORMAT=json`, умолчание в продакшене).
Такие логи читают Loki, ELK и Yandex Cloud Logging без парсеров-эвристик.
В разработке формат человекочитаемый.

```json
{"ts":"2026-08-04T20:15:03.412Z","level":"info","event":"http.request","request_id":"a1b2c3d4e5f60718","user_id":7,"method":"POST","route":"/api/contacts","status":201,"duration_ms":12.4}
```

* `request_id` протягивается через весь запрос и возвращается заголовком `X-Request-Id`.
  Если заголовок пришёл снаружи — он сохраняется, и трассировка сшивается с балансировщиком.
* Поля `password`, `token`, `secret`, `code` и подобные заменяются на `***`
  до записи — секрет не попадёт в лог даже случайно.
* Служебные опросы (`/api/health`, `/api/ready`, `/api/metrics`) в лог не пишутся.

`LOG_LEVEL`: `debug` | `info` | `warn` | `error`.

## 7. Метрики и проверки для балансировщика

| Эндпоинт | Что означает | Кому |
|---|---|---|
| `GET /api/health` | процесс жив и отвечает | докер, супервизор |
| `GET /api/ready` | можно слать боевой трафик | балансировщик, Kubernetes |
| `GET /api/metrics` | метрики в формате Prometheus | мониторинг |

`/api/ready` проверяет базу, версию схемы и файловое хранилище, а при остановке сразу
отвечает `503` — балансировщик успевает увести трафик до закрытия сокета.
Недоступность S3 в готовность не входит: запись падает на локальный диск, узел рабочий.

Метрики, за которыми стоит следить (первые две — целевые показатели из плана):

| Метрика | Смысл |
|---|---|
| `http_request_duration_seconds` | время ответа; корзина `le="0.3"` — цель «карточка быстрее 300 мс» |
| `http_requests_total{status}` | доля пятисоток и четырёхсоток |
| `db_query_duration_seconds` | время обращений к базе |
| `db_errors_total` | ошибки запросов |
| `backup_runs_total{result}` | `success`, `verify_failed`, `error` |
| `inbox_messages_total{channel,direction}` | поток обращений по каналам |

Идентификаторы в путях сворачиваются в шаблон (`/api/contacts/:id`) — иначе тысячи
временных рядов убивают Prometheus.

Метрики не стоит публиковать наружу: в `deploy/nginx.conf` доступ к `/api/metrics`
ограничен внутренней сетью.

## 8. Проверки перед релизом

```bash
npm run check     # линтер + все тесты
```

Линтер (`tools/lint.js`) написан без ESLint и проверяет то, что ломает продакшен:
синтаксис, забытый `await` на вызове слоя данных, `console.log` вместо структурированного
логгера, подстановку значения в SQL вместо параметра, отладочные хвосты и появление
внешних npm-зависимостей.

CI (`.github/workflows/ci.yml`) на каждый коммит: линтер, тесты на SQLite, тесты на
PostgreSQL с сервисом-базой, матрица версий Node, сборка образа и проверка,
что контейнер выходит в готовность.

## 9. Корректная остановка

По `SIGTERM` приложение снимает себя с готовности (`/api/ready` → `503`), останавливает
фоновые задачи, дописывает текущие ответы и закрывает базу. На всё даётся 15 секунд,
после чего процесс завершается принудительно. В systemd-юните `TimeoutStopSec=30`,
в Dockerfile — `STOPSIGNAL SIGTERM`.
