# Обновление витрины: варианты, фото и импорт

Этот документ описывает состояние именно этого архива и имеет приоритет над старыми README о патчах. Изменения рассчитаны на Node.js 22+ и исходный проект из приложенного архива. Боевой сервер и его база не менялись.

## Что изменено

- У варианта есть цвет, описание, цена, фотографии и свой структурированный статус наличия. Пустое описание/наличие наследуются от товара. Изменения варианта сохраняются отдельной кнопкой; не отправляйте массив `variants` в `PUT /api/store/products/:id`: теперь это явная ошибка вместо молчаливого игнорирования.
- Выбор цвета в карточке меняет изображение, подпись наличия, описание, цену и вариант в заявке. При нескольких фотографиях появляются стрелки; для варианта без фото используется общее фото, а при его отсутствии — заглушка. Недоступный вариант нельзя забронировать, сервер дополнительно проверяет его статус.
- Редактор получает товар по ID, сохраняет ещё не отправленные поля при перерисовке и прокручивается в окне CRM. Сначала сохраните вариант, затем загружайте его фото.
- XLSX-парсер учитывает namespace и пустые ячейки. Импорт товаров выполняется в транзакции с сохранением по строкам; пробный прогон моделирует предыдущие строки и откатывает изменения. Пустые значения не очищают ранее сохранённые поля и не снимают товар с публикации. Неоднозначный SKU товара отклоняется.
- В мастере импорта доступен пример `public/catalog-import-template.csv`. Повторяйте SKU модели в каждой строке и задавайте уникальный в пределах модели SKU варианта. Пустые ячейки означают «не менять». Новые товары без статуса создаются черновиками; варианты ищутся по SKU, а без него — по названию в рамках товара.
- «Импорт папки товаров и фото» принимает одну таблицу CSV/XLSX и JPG/PNG/WebP. Таблица проверяется и подтверждается отдельно; затем проверяется и отдельно подтверждается привязка фотографий. Можно загружать и только фото. Имена папок должны точно совпадать с SKU, названием или slug товара, а подпапка — с SKU, названием или цветом варианта. Пример:

```text
папка-импорта/
  catalog.csv
  MODEL-001/
    MODEL-001-WHITE/
      01.png
      02.jpg
    MODEL-001-BLACK/
      01.jpg
```

- Неоднозначные файлы и файлы в неизвестной подпапке варианта не записываются как общее фото. Список результатов выводится в окне. Повторный импорт одинакового файла к тому же варианту распознаётся по хэшу. Импортированный ранее файл без хэша может не распознаться как дубликат. Большие папки обрабатываются последовательно с паузами из-за ограничений API.
- Новые фото каталога сохраняются в `STORAGE_DIR/catalog`, по умолчанию `DATA_DIR/files/catalog`, и входят в файловую часть локальной резервной копии. Прежние ссылки `/uploads/catalog/...` не меняются; при отсутствии файла в новом месте предусмотрено чтение старого `public/uploads/catalog`.

## Ограничения и проверки

- Массовое создание по папке требует сопроводительной таблицы. По одним только названиям папок новые карточки автоматически не создаются. Папочный мастер показывает автосопоставление, но для ручной настройки колонок используйте отдельный мастер XLSX/CSV. Ошибки импорта показываются в интерфейсе, первые 20 ошибок сохраняются в статистике.
- Вариантный статус регулирует бронирование; подписки на поступление остаются на уровне товара. Старые общие фотографии автоматически к цветам не привязываются.
- Тесты: профильный набор — 50/50, линтер успешен. На локальной временной SQLite базе в Chromium проверены мобильная карточка, галерея, выбор варианта, бронирование, редактор и папка с таблицей/фото. PostgreSQL и действующая инфраструктура не проверены.
- Полный `npm run check`: 208 из 220 тестов прошли, 12 не прошли. Они воспроизводились в исходном архиве: два ожидают другой интерфейс/автопривязку, восемь зависят от отсутствующих демонстрационных данных или текущих SEO-ожиданий, ещё два относятся к отсутствующему `mailserver.env` и расхождению поля почтового webhook. Это не подтверждение безопасности всего релиза. Перед production требуется разбор этих тестов и приёмка на копии реальной базы.

## Перед обновлением сервера

1. Проверьте `git status`: сохраните локальные изменения, не используйте `git reset --hard` и не удаляйте `.env`, данные и `public/uploads`.
2. Убедитесь, что команды `npm run backup` и `npm run migrate` получают **те же** `DATA_DIR`, `STORAGE_DIR` и `DATABASE_URL`, что процесс PM2. Обычно конфигурация читается из `.env`, но значения окружения PM2 могут иметь приоритет. Если это неизвестно, сначала выясните конфигурацию; иначе можно сохранить или мигрировать не ту базу.
3. Остановите процесс, сделайте и проверьте резервную копию реальной базы и файлов. Старый механизм backup не включал `public/uploads/catalog`, поэтому его также сохраните отдельно. Храните копию вне каталога проекта.
4. На копии БД заранее проверьте миграцию `019_variant_details.sql`. Если на сервере уже есть другая миграция 019, не перезаписывайте её: требуется согласовать версию.
5. После обновления старые фото можно оставить в `public/uploads/catalog`, но для постоянного хранения и будущих backup скопируйте их без перезаписи в фактический `STORAGE_DIR/catalog` (по умолчанию `DATA_DIR/files/catalog`). Проверьте права пользователя PM2 и что каталог расположен на постоянном диске. Существующие файлы в обоих местах не удаляйте до проверки. Если настроен S3 для вложений, фото каталога всё равно используют этот локальный каталог, поэтому постоянный диск необходим.
6. Новые записи БД после миграции несовместимы со старой версией: для отката сначала остановите приложение, восстановите согласованную копию базы и файлов и только затем старый код.

## Краткие команды

После переноса содержимого архива в **существующий локальный Git-репозиторий**:

```bash
cd /путь/к/локальному/репозиторию
git status
git add .
git commit -m "Fix storefront variants and catalog import"
git push origin HEAD
```

На сервере, только после проверки конфигурации и сохранения изменений/копии старых фото:

```bash
cd /var/www/vapelab
git status
pm2 stop vapelab
npm run backup             # проверить успешное завершение и восстановимость
git pull --ff-only
npm ci --omit=dev
npm run migrate
pm2 restart vapelab --update-env
pm2 logs vapelab --lines 50
```

Если backup, pull, установка или миграция завершились ошибкой, не продолжайте автоматически. После запуска проверьте `/api/health`, страницу существующего товара с вариантами и фотографии. Не запускайте очистку базы (`npm run reset`).
